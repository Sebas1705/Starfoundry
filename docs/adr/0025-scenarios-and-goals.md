# 0025. Scenarios are data files with goals, a story and a goals engine

- Status: proposed
- Date: 2026-11-22
- Area: simulation, content, gameplay
- Design: [modes, scenarios and resources](../superpowers/specs/2026-11-22-modes-and-scenarios-design.md), part B

## Context
The game had one fixed goal (`GameOutcome`: clear the goal waves with a station standing) and one fixed start (the starter ship). Story levels, a sandbox with player-chosen options and a campaign whose goal is data all need the same three things: a description of how a game starts, a list of goals to evaluate, and a few lines of story. A save or a replay must rebuild the same start, so what a scenario changes in the world has to be part of the command-log header ([ADR 0016](0016-saves-are-the-command-log-replayed.md), [ADR 0023](0023-world-rules-and-difficulty.md)).

## Decision
- **Scenario files.** `content/scenarios/<id>.json` (id equals the file name), loaded and validated by `ScenarioCatalog` against the content: unknown properties, duplicate ids, unknown items, research nodes, module kinds and structure templates, out-of-range numbers and bad story triggers are errors. A `ScenarioDef` holds the names, descriptions and briefing in es and en, an order, the rules (a preset id plus any explicit override of a `WorldRules` field, and starting items), the start (structures built from content templates at an offset from home, starting items, a seed or 0 for "the game picks one", an optional home archetype), the primary and secondary goals, story beats and the star rules. The schema and an example are in [the scenarios prototype](../prototypes/scenarios.md).
- **Goal types.** `survive_waves` (the count, or the rules' goal waves when omitted), `research`, `produce`, `mine`, `visit_systems`, `found_stations`, `build_module`, `keep_alive` (fails when a module of the kind, or of any kind, is destroyed) and `keep_fuel` (fails when a reactor runs dry). Each goal has an id, es and en text and an optional time limit. `keep_alive` and `keep_fuel` never complete: they hold or fail.
- **Structure templates.** `structure_templates` in the content now holds any number of templates by id (the starter ship is `starter_ship`); the other templates are mixed into the content hash only when present. New: `siege_station`, `siege_ship`, `cold_ship`, `blank_station`.
- **World creation.** `SimWorld.CreateScenario(content, scenario, seedOverride, rules)` builds a structure world (campaign mode, or sandbox mode for a sandbox scenario) from the scenario: the rules, every start structure (the ship at the home origin, the others at their offsets) and the starting items. `rules` replaces the scenario's effective rules so the sandbox and the campaign can use player-chosen ones, and so a replay can pass the rules of the log header.
- **Header version 8.** Flags bit 4 (value 16) says the world came from a scenario; the header then carries, after the rules block, an int length and the UTF-8 scenario id. The header's content hash is then `ScenarioDef.HeaderHash`: the content hash mixed with the scenario's *world-building* hash (id, mode, seed, rules and start structures), not its goals or texts, so fixing a translation or a goal never invalidates a save. Versions 5 to 7 read as no scenario; a version 7 header that sets bit 4 is refused. `SaveGame.Write` takes the scenario, `SaveGame.Read` a `ScenarioCatalog` (a scenario save without the scenario is refused), `SaveInfo.ScenarioId` reports it and `SimWorld.ReplayScenario` rebuilds a game from a log.
- **Progress counters in the simulation.** `ProducedTotal(item)` (machine outputs, ship crafting, hand mining, drones), `MinedTotal(item)` (hand, drones, drills), `StationsFounded`, `ModulesBuilt(kind)` (placement commands only), `ModulesLostOf(kind)`, `FuelStarvedTicks` and `VisitedSystemCount`, next to the existing `ResearchedCount`, `IsResearched`, `WavesSpawned` and `ModulesLost`. They only grow, are cloned and validated, and are deliberately **not** mixed into the checksum: they are pure bookkeeping of events that are hashed anyway, and mixing them would change every existing golden checksum.
- **The goals engine.** `ScenarioProgress` (engine-free, in `Starfoundry.Ui`) is updated every tick-batch. It marks goals done or failed and keeps when, fires each story beat once (`start`, `goal:id`, `fail:id`, `time:seconds`, `win`, `lose`), and decides the outcome: Lost when the ship is lost, a primary keep goal fails or a primary goal's time limit passes; Won when every primary goal is done (a keep goal that never failed counts). A done goal stays done and a decided outcome is final, so the game can go on after a win. Stars: one for a win, two or three when the win is within the time bounds with enough secondary goals. `OutcomeReason` gains `GoalsDone` and `GoalFailed`.
- **The campaign is a scenario too.** `campaign.json` has no start of its own, lets the player choose the rules and the seed (`player_rules`), and asks for the rules' goal waves, a station and a second system visited. `GameOutcome` is unchanged and still decides the existing game; see the consequences.
- **The levels** (the five story levels, the campaign and the sandbox templates) and their measured bot times are in [the scenarios prototype](../prototypes/scenarios.md).

## Consequences
- Benefits: a level is a JSON file and a test; saves and replays carry the scenario; the sandbox is "a scenario without goals" with player rules; the same goal definitions drive the HUD, the end screen and the bot.
- Costs: a version 8 log cannot be read by a build that only knows version 7; a scenario save breaks when the scenario's rules, seed, mode or start structures change (not its texts or goals); the goal progress after loading a save is recomputed from the world, so the recorded completion times of goals restart unless the game stores them or steps the loaded world in small batches.
- How it is checked: `ScenarioTests` (loader errors, creation, header and save round trips, the counters), `ScenarioProgressTests` (every goal type, time limits, keep goals, story, stars, the shipped levels), `ScenarioContentTests` (texts in both languages, numbers, every goal deliverable, reachability of levels 4 and 5, the bot winning levels 1 to 3) and the unchanged golden checksums.
- Known gap: `GameOutcome` does not yet ask for a jump, while `campaign.json` does. When the balance pass that makes a jump part of the win lands, `GameOutcome` and the campaign scenario agree; until then the scenario is the stricter of the two.
- Part D (the New Game screen, the goals panel, the end screens, the progress file and the goals sidecar of a save) is built; see [the scenarios prototype](../prototypes/scenarios.md#the-game-ui-part-d). The sidecar stores the per-goal done and failed seconds, the fired story beats and the decided outcome next to the save, so the recorded completion times survive a load.
- Not decided here: a level editor, more levels.

## Alternatives considered
- **Goals as code, one class per level.** Rejected: levels would need a build, and the bot, the HUD and the tests could not read them.
- **The whole scenario set in the header hash.** Rejected: adding a level or fixing a text would invalidate every save of every other level.
- **Mixing the counters into the checksum when non-zero.** Rejected: any world that had crafted something would hash differently from before, so every golden checksum would change.
- **Scenario rules held in the content file.** Rejected for the reason of [ADR 0023](0023-world-rules-and-difficulty.md): they would change the content hash and could not be chosen per game.
